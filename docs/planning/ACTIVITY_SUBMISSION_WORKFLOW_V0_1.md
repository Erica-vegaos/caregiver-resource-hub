# 聽見你｜活動回報與新增資訊工作流

版本：v0.1.0｜2026-11-14（Asia/Taipei）
狀態：流程與驗證提案；尚未新增表單、API、資料庫或部署。
範圍：活動資訊投稿與既有活動錯誤回報；不包含匿名心事、報名代辦或個案求助。

## 1. 現況與本輪決定

已核對 main：網站由 templates/index.html 經 src/build.py 產出 dist/index.html，wrangler.jsonc 僅設定靜態資產；沒有接收 POST、持久待審佇列、管理者認證或回執查詢。
data/review.md 是建置產物，不是使用者投稿收件匣。data/events.json 也是建置輸出，不能直接當人工修改入口。

第一階段先完成此流程及桌面演練；正式功能必須在接收、保存、審核與發布四段都有可驗證出口後才開放。禁止只加表單、用本機收藏假裝送出，或把未查核投稿自動刊登。
本文件的欄位、時限及技術路徑均為設計決策，並非現有能力或外部服務保證。

## 2. 使用者工作流

### 回報既有活動

1. 在活動詳情選「回報資訊」，帶入不可由使用者任意覆寫的活動 ID；標題、場次與原公告供確認。伺服器仍需查證 ID 存在。
2. 選問題類型：時間／地點、參加資格、費用、報名連結、取消／改期、重複、其他資訊錯誤。
3. 可補充原公告或更正連結、簡短說明。只有選「其他」時說明必填；不要求姓名、電話、病史或家屬身分。
4. 送出前提示「請勿填入個人病況或他人資料；回報會先核對，不會立即改動活動」。
5. 接收端驗證並成功保存後，顯示收件編號與「已收到，待核對」。無持久保存不得回成功。
6. 失敗時保留本次畫面輸入，顯示可重試原因；不能跳成功頁或自動清空。

### 提供新活動資訊

1. 頁面固定入口「提供活動資訊」，空結果也提供同一入口，不另建一套表單。
2. 必填：原公告 HTTPS 網址。選填：活動名稱、地區、日期原文及簡短補充；盡量讓使用者貼連結即可。
3. 說明「僅收錄精神疾病家屬可參加的活動、團體、課程與講座；提供資訊不代表完成報名或保證刊登」。
4. 送出、收件與失敗處理沿用回報。投稿身分不等於主辦單位，不顯示已認證標章。
5. 只有圖片／無公開原公告：先不接受附件，使用者可貼公開公告頁；無法核對的內容留待補證，不憑敘述補齊。

兩條流程皆不要求登入、不蒐集聯絡方式、不承諾逐件回信。初版回執是收件證明，不開放公開投稿列表或憑連號查詢內容。

## 3. 內部處理與狀態

維護者為 Erica；Agent 可整理候選、差異及檢查結果，人工核准後才進入刊登程序。提交者不能自行核准。
初版用固定每週一次待審檢視作人工安排；此安排尚未建立排程或通知，不對使用者承諾處理天數。取消／資格錯誤在每次檢視時優先處理。

| 狀態 | 進入條件 | 下一步／責任 |
| --- | --- | --- |
| received | 伺服器驗證且持久保存成功 | 維護者開始查核 |
| reviewing | 已開始核對原公告 | 核對場次與欄位證據 |
| needs_evidence | 原公告不足、受限或互相矛盾 | 保存缺項；不猜填、不公開原始投稿 |
| approved | 證據完整且核對通過 | 維護者建立資料修改 PR；尚未對外發布 |
| resolved | 新增／更正已發布並驗證，或確認無需變更 | 記結果類型、理由、PR、版本與線上驗證時間 |
| rejected | 不在範圍、惡意或無效內容 | 記最小理由後結案 |
| duplicate | 確認同一投稿目的與場次 | 連到主件；不重複改資料 |

allowed transitions：received → reviewing／rejected／duplicate；reviewing → needs_evidence／approved／resolved（限無需變更且有查核理由）／rejected／duplicate；needs_evidence → reviewing／rejected；approved → resolved／reviewing（資料變動或發布失敗）。
結案件如有新證據，建立關聯新件，不靜默覆寫結案紀錄。
每次轉態記錄操作者、時間、前後狀態與原因。並行修改須比對 revision，衝突不能最後寫入者無聲覆蓋。

### 原公告查核規則

- 回報：比對指定 ID、來源及實際場次；原單位明確更正才改時間、地點、資格或取消狀態。
- 網址失效、404、逾時不能當作活動取消；原文無費用不當免費；看到報名按鈕不當尚有名額。
- 未查證的取消回報先提高審查優先級，不由匿名使用者直接下架活動。必要的「待確認／暫停推薦」只由維護者在有理由時核准，並留稽核。
- 新增：確認家屬可參加、日期年度、地區／線上限制、場次、主辦、原公告、費用與報名狀態。未知欄位保留未知；日期、資格等必要證據不足則 needs_evidence。
- 沿用既有 validate_event、prepare_events、deduplicate；但驗證器通過不等於證據真實，仍需人工讀原公告。
- 同 URL 的系列不同日期不可直接合併；疑似重複只標記。只移除已知追蹤參數，保留活動 ID 參數。
- 新增或更正先修改真正的來源輸入：人工資料在 manual_records.json／national_records.json；HTTP 來源需對照 parser／來源規則。不要只改 events.json，下次建置會覆蓋。
- HTTP 活動的人工更正可能被 overlay_records 覆蓋：實作前須測同 ID 優先順序及後續 refresh 行為，建立有證據、有適用期限的更正策略，避免舊人工更正永久蓋住新公告。
- 新來源先人工模式，不因有人投稿就加入自動抓取白名單。

## 4. 接收與保存方案（建議）

建議延續 Cloudflare，增加同站接收 API 與私有持久待審儲存；優先評估 Worker + D1。這是規劃，需先核對實際帳號、binding、認證、配額與部署方式，不假設已可用，不新增付費服務。
不把原始投稿寫入公開 GitHub Issues、JSON 或公開 logs；公開 repo 只保存核准後的活動事實與必要來源證據。

| 元件 | 最小責任 |
| --- | --- |
| POST /api/submissions（擬） | 驗證 kind、欄位、長度、活動 ID、防濫用、冪等，交易寫入待審及初始稽核 |
| 私有待審儲存（擬） | 投稿本體、狀態、revision、稽核；不得混入靜態 dist |
| 受保護管理入口（擬） | 維護者查看、查核、轉態；每個管理 API 都驗證身分，不能只隱藏網址 |
| 現有 GitHub 資料 PR | 僅核准事實、差異與證據；經測試與建置後合併 |
| 發布後驗證 | 對應 commit、公開頁資料與狀態；成功後才能 resolved |

建議最小資料合約：
- schema_version、id（隨機不可枚舉）、kind（report／new_event）、event_id（report 必填）、issue_type（report 必填）、source_url、description、optional_title／city／date_raw。
- status、created_at（伺服器含時區）、updated_at、revision、idempotency_key、payload_hash。
- review_reason、decision_type、related_submission_id、published_event_id、publication_commit、verified_at。
- 稽核獨立 append-only 記錄 submission_id、actor、from_status、to_status、reason、at；不保存不必要的原始全文副本。

建議限制：JSON body ≤8 KiB，URL ≤2,048 字、說明 ≤1,000 字、標題 ≤200 字，拒絕未知欄位。固定枚舉及伺服器驗證不依賴前端。
初版純文字、無附件、無 HTML，無自動打開使用者網址。顯示內容一律 escaping。HTTPS 檢查只作輸入驗證，不等於可安全抓取；未來要抓網址時另外驗 DNS、redirect、私網與大小限制。
同源 Origin 檢查、防重送、伺服器端頻率限制與簡易機器人攔截一起設計，不能只靠停用送出按鈕。限制所需識別採短期保存，避免記錄原始 IP；受限或儲存失敗時回清楚錯誤。
冪等鍵相同且 payload 相同回原收件編號；相同鍵但內容不同回衝突；不同人回報同場不同問題仍可各自保存。若網路中斷，重試使用原鍵，不能為每次重試產生新件。

保存政策提案：未結案原文最多90天，結案原文30天後清除；未結案件到期前須檢視或標記到期無法查證，不可假裝完成。只保留不含原文與個資的最小審核摘要及核准事實。需實際驗證刪除涵蓋 logs、匯出與備份的服務保存邊界；做不到時先調整公開說明再開放。
初版不做電子郵件通知、狀態查詢或自動抓連結，縮減維護面。

## 6. 先演練、再開發的驗證門檻

### Gate A：流程桌面演練（尚未驗證）

使用明確標示的合成樣本，不修改真實活動或假裝是實際投稿。逐件記錄輸入、狀態轉移、證據、負責人、預期資料差異、結案依據與耗時。
至少演練：正確更正、假取消、原公告失效、合格新活動、病友限定誤投、系列不同日期、同件重送、缺必要日期證據、HTTP更正後重新刷新。
通過標準：每件有唯一且合理的去向；未查證資料零自動公開；每個 needs_evidence 說清楚缺什麼；每個 resolved 有線上驗證或無需變更證據。
此文件只有案例設計，不宣稱已跑完這些演練。

### Gate B：接收／審核整合驗證（實作後，開放前）

| 案例 | 預期結果／證據 |
| --- | --- |
| 合法 report 與 new_event | 各成功保存一次，重啟後仍可由授權管理者讀到；前端收到隨機收件編號 |
| 假 event_id、錯誤枚舉、空網址、超長與未知欄位 | 4xx，不寫入、不回成功；說明可修正欄位 |
| javascript／file／內網 URL | 拒絕；無對外擷取；公開 HTTPS 頁亦不自動 fetch |
| 重送／逾時後重試／並行重送 | 相同鍵與內容只一件；鍵相同內容不同為衝突 |
| 惡意 HTML／script 及私人內容 | 純文字呈現，不執行、不出現在公開產物或 CI log |
| 未登入／偽造狀態／無效認證 | 無法讀佇列、修改狀態或核准；公開 POST 不能自帶 approved |
| 狀態跳躍／revision 過期 | 拒絕，原狀態不變；合法轉態有稽核 |
| 斷線／儲存失敗／限流 | 不顯示成功、不清空輸入，可依類型重試；交易失敗不留半筆 |
| 未核准候選與取消回報 | 網站、搜尋與 dist 中均無未核准變更 |
| 已核准但建置／部署失敗 | 保持 approved 或退回 reviewing，不能 resolved |
| 清理到期資料 | 原文確實消失；最小審核摘要可保留；保留邊界有記錄 |
| 行動裝置及鍵盤 | 320／390px 無溢出；欄位有 label，錯誤可聚焦，送出狀態可讀，關閉後回原入口 |

### Gate C：刊登與回歸（實作後）

1. 對同一組合成新增／更正測 source → validate → prepare → build → 搜尋輸出，不能只測表單函式。
2. 實測修正 HTTP 活動後 refresh 不被意外復原，也不讓已過期人工更正永遠蓋住較新來源。
3. 執行 python -m unittest discover -s tests -v、node --test tests/test_search.cjs 與離線 python src/build.py；確認原有收藏、行事曆、搜尋與未知狀態維持正確。
4. 在隔離預覽環境完整送件、由維護者查核、發布測試資料、檢查公開結果，再清理合成紀錄。
5. 正式發布確認公開頁屬於指定 commit；更正欄位、原公告、取消／截止狀態與收藏 ID 正確，才將對應件 resolved。
6. 新 API 故障時活動搜尋仍可用；回退靜態版本時待審私有資料保留，並禁止出現已停用的假送出入口。

## 7. 實作順序與停止條件

1. 本輪：提交流程、影響依賴、驗收規格至 GitHub，供檢視。
2. 下一階段先跑 Gate A 並記錄結果，再確認接收儲存與管理認證實際可用。缺任何一段就停在規劃，不先上表單。
3. 建立單一「活動資訊提交」模組，report／new_event 共用接收、待審與稽核；先接收端，再管理處理，再前端。
4. 通過 Gate B、C 才開放正式入口；自動刊登、對外聯絡、附件與使用者帳號另案處理。

停止條件：只有前端無持久保存、只能把原文放公開 repo、未授權者可讀待審、無審核出口、無法證明 refresh 後更正仍正確、或正式版無可驗證發布路徑。
以上任一成立，維持現有查詢站功能，不宣稱已提供回報或新增活動能力。
