# 有伴｜最低 token 自動化方案

版本：v1.0.0｜2026-11-14（Asia/Taipei）｜狀態：規劃，未啟用排程。

## 決策

日常營運以 Python 規則、HTTP 快取和資料狀態機執行，預設不呼叫 LLM、不依賴 ChatGPT 每日閱讀整站。目標為一般更新日 0 個 LLM API token；網路流量、儲存、CI 執行時間仍是不同的成本，不能稱作全部零成本。建立來源解析器時才可能使用開發對話 token。

第一階段不開 LLM API；規則處理不了的少量候選先進人工待審。已有穩定模板後才開放自動刊登；不要以模型自評信心作為唯一上架條件。

## 與現有程式的差距

| 項目 | 現在已有 | 還需實作／驗證 |
|---|---|---|
| 過期處理 | build.qualify 依時間歸檔，前端預設排除已結束；保留歷史 | 已開啟頁面跨過結束時間自動重算、到期輸出每日更新 |
| 抓取 | 兩個特定網站模板、3個種子詳頁、臺北列表第一頁候選發現 | 通用來源排程、列表翻頁、增量抓取、條件HTTP快取、流量限制 |
| 去重 | 最新查核優先；ID、原網址＋場次、標題＋主辦＋場次比對 | 網址追蹤參數正規化、跨來源群組、保留所有證據、改期identity |
| 品質 | 家屬資格、明確時區、證據、未知費用、失敗保留、隔離候選 | 每來源真實樣本基準、重複運行、異常批次阻擋 |
| 全台 | 26筆來源／缺口入口，22縣市可搜尋 | 各地方來源不等於已可抓取；逐一啟用adapter |
| 發布 | 人工私人Sites發布；GitHub手動refresh工作流程檔已準備 | GitHub寫入權限、持續資料狀態、正式部署串接；目前皆未啟用 |

## 更新頻率：每日查列表，不每日重爬全部詳頁

以下為起始設定，依來源更新量與可接受存取頻率調整，不代表已執行。

| 工作 | 建議頻率 | 是否爬網頁 | LLM token |
|---|---|---|---|
| 到期隱藏 | 每次開頁、篩選及前景每60秒重新計算；每日產出一份最新資料 | 否 | 0 |
| 活躍機構活動列表／RSS | 每日1次，目標台灣時間06:17附近 | 是，先查列表 | 0 |
| 新詳頁、已變更詳頁 | 發現後同一批次，使用去重佇列 | 是 | 0（支援模板） |
| 7天內活動／7天內截止報名 | 每日1次檢查詳頁 | 是，優先排程 | 0 |
| 8–60天未來活動 | 每3天1次 | 是 | 0 |
| 更遠日期／低頻公告 | 每週1次 | 是 | 0 |
| 已結束活動 | 停止例行抓詳頁，保留修正入口 | 否 | 0 |
| 全國名錄、來源網址異動 | 每月1次 | 是 | 0 |
| 人工待審 | 每週一次，集中處理新模板／必要欄位問題 | 不必重新全站搜尋 | 0（預設不使用AI） |

列表沒有更新日期時：只重新抓當前列表第一頁，解析連結集合；每週做有限回溯頁面，防置頂、補刊、順序變動造成遺漏。不能遇到第一個舊網址就永久停止翻頁。RSS/API/結構化資料優先於HTML；僅在必要且允許時使用瀏覽器渲染，不把瀏覽器Agent當日常爬蟲。

GitHub Actions可用cron啟動Python；時區明確使用UTC，對應06:17為前一日22:17 UTC（`17 22 * * *`），不是精準準時保證。選非整點降低尖峰影響，另用 last_run_at 偵測漏跑。公開repo排程長期無活動可能停用，需保留手動補跑。此文件沒有新增或啟用cron。

## 怎麼爬：少下載、少解析、不送整站給模型

1. **固定來源登錄**：只有status=enabled且完成adapter驗收的來源可排程。登錄含list_url、adapter版本、允許網域、更新頻率、解析政策及last_success；名錄中的directory/blocked不可當成自動抓取已就緒。
2. **一次條件GET**：保存ETag/Last-Modified，下次帶If-None-Match/If-Modified-Since。304則使用舊內容，不再下載正文；不先HEAD再GET把每次請求數翻倍。若來源不支援，照常GET後比較內容hash。
3. **抽取活動區塊**：只取活動正文與必要連結，移除選單、footer、廣告與瀏覽計數。保留正文hash與parser_version；正文、模板均未變時不重新解析。
4. **列表發現與詳頁更新分開**：new URL入佇列；既有未來活動按到期策略重查，因為列表標題不變不代表報名狀態、時間、地點沒變。
5. **以URL為抓取單位**：同頁列12場系列，只抓一次，再產出12個場次。相同網址同批次只請求一次；同網域串行，建議間隔2–5秒、timeout20秒、單頁2MB上限、每批總頁數上限。
6. **規則解析及驗證**：確定年份／時區、活動日期、家屬資格與來源證據。費用未寫就是unknown；「額滿為止」不等於尚有名額。沒有可信模板的新候選進待審，不直接上架。
7. **失敗退避**：尊重Retry-After；逾時或5xx最多有限重試後標記失敗，下一輪退避。不繞過登入、驗證碼或存取限制。一次失敗不刪活動、不推定取消。

304只能更新HTTP驗證時間；正文未變且已有可信解析結果時，才可保留該結果為已重驗。手動查核但未建立語意解析規則的來源，不因下載成功就刷新人工checked_at。last_fetch_at、last_content_validated_at、last_manual_checked_at分開保存。

## 過期下架：靠日期，不靠爬蟲發現

- 以Asia/Taipei和明確start/end計算；只有日期時以當地該日結束為界，前端不顯示捏造鐘點。
- `end < now`：自動移出「未來活動」，保留歷史及來源；不物理刪除資料。
- 報名截止但未結束：標為「已截止」，保留在全部未來活動供查詢；提供排除已截止條件。報名截止不能當成活動結束。
- 明確取消：立即停止列為可參加場次，保留取消紀錄。宣布延期卻未公布新日期：移至待確認，不沿用舊日期繼續推薦。
- 來源抓不到：保留最後有效資料、標示待確認，不誤刪。來源連續失敗進一次合併維護報告。
- 不確定結束日期的常態團體：不可永遠當成近期場次；保留來源入口或待審，取得實際日期再上活動清單。

因此就算今天爬蟲失敗，已開頁面或重新查詢仍能排除時間已過的場次；長期沒有成功更新仍須呈現資料新鮮度警示。

## 怎麼去重：三層比對，改期與系列分開處理

| 層次 | 識別方式 | 處理 |
|---|---|---|
| 同一來源同活動 | source_id＋來源原生event_id＋穩定occurrence_id | 更新原記錄，不新增；時間改動保留version與diff |
| 同網址重複發現 | canonical_url＋穩定場次識別 | 同一批只抓一次；同頁不同日期仍是不同場次 |
| 跨網站轉貼 | 主辦者正規化＋標題＋日期／時間＋地點的比對 | 高度確定才組成同一canonical_event，保留所有source_links與證據；模糊者待審 |

網址正規化：移除fragment及確定為追蹤用途的utm_*/fbclid等，排序query；保留id、ss、活動識別與報名參數，不隨意將http升https或合併不同路徑。台／臺、空白及全半形正規化。主辦者別名用人工可審核對照表。

重點：新日期不能永遠作為唯一identity，否則活動改期會產生兩筆；有原生ID時先識別原活動再更新時間。單頁系列沒有原生場次ID時，保存穩定occurrence與來源位置對照；不確定是改期或加場就待審，不自動覆蓋。『每月家屬支持團體』等同名標題不能只憑文字相似刪掉。

同一活動來源衝突優先原主辦公告；時間／資格／費用衝突不讓最新抓取時間任意覆蓋，保留衝突證據並待確認。cross-source先群組再呈現，避免丟失第二來源。

## 真正需要AI時的上限

預設關閉AI。需啟用時只處理「新模板或規則無法判斷的變更區塊」，不處理重複或過期資料，不每日重新呼叫所有Agent。

- 先做HTML清理，輸入僅必要段落，建議單件上限約2000輸入token＋500輸出token（工程預算，不是實測用量）。
- 快取key = source_url＋正文hash＋parser_version＋prompt_version；相同內容不重問。
- 例如每月10個例外，上限預算約25000 token；若規則全部可處理，當月為0。實際用量由模型tokenizer與usage紀錄計算，不用中文字數冒充token數。
- 超出每月預算進人工待審，不連續重試、不自動換更大模型。不要用多Agent對同一篇公告重複分類。
- 模型只提出候選與證據，程式驗證後仍不確定就人工確認；將常見例外改善成固定adapter，降低下一個月成本。

## 排程執行與網頁發布分開

`抓取→驗證→去重→產出events.json與人工待審→通過測試→發布同一版資料→記錄成功時間`。

GitHub Actions適合跑Python；不能以「workflow跑完」冒充網站已更新。現有私人Sites是獨立託管，GitHub push尚不會自動更新它。需選定受支援的部署串接，或未來讓前端讀取固定資料端點；不把一次性Sites憑證存入GitHub。部署失敗保留上一版，待重試，不在來源失敗時發布空資料庫。

最低維護方式是先驗證2個既有adapter，加2–3個新來源，連續跑14天再擴張；不是一次開26個未知爬蟲。人工看新模板／資格衝突／持續失敗，不逐筆重看所有活動。通知只在新異常或狀態改變時合併一次；同一故障不每天重複轟炸。

運行狀態與HTTP快取需持久保存（如受控資料分支或SQLite持久儲存）；GitHub runner本機硬碟是暫時的，僅用Actions cache可失效，不可作唯一真相資料庫。隔離raw候選與已核准published快照；每筆變動保留來源及時間。

## 實作順序與驗收

1. 恢復GitHub Contents寫入權限，推送目前版本及本文件；這一步目前403阻擋。
2. 增量爬取：HTTP快取、URL抓取去重、持久來源狀態、每來源排程與退避，測試304／正文不變／頁面改版／單頁多場。
3. 活動生命週期：前端跨時點重算、報名截止與過期分離、延期未定隔離；測試午夜、全天活動及series加場／改期。
4. 跨來源群組與人工待審：測試轉貼、同名不同場、不同主辦同日、改期、query識別參數。
5. 使用者確認固定執行環境與部署串接後啟用每日作業；先手動完整跑一次並確認網站資料版本，再開cron。本文僅規劃，沒有建立排程或新增付費服務。
6. 連續14天記錄抓取成功率、新增候選正確率、誤合併數、失敗恢復、人工維護時間及LLM用量，再決定是否擴張。
